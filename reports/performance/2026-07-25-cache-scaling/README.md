# 과목 조회 캐시 및 Cloud Run 확장 벤치마크

측정일: 2026-07-25 (KST)

## 목적

과목 조회 API의 병목을 다음 순서로 분리해 측정했다.

1. 운영 중인 무캐시 애플리케이션의 기준 성능
2. 동일한 Cloud Run 사양에 Caffeine 캐시만 적용한 성능
3. 캐시 적용 후 1,000 VU에서 단일 인스턴스의 한계
4. DB 연결 예산을 제한한 상태에서 Cloud Run 수평 확장 효과
5. Supabase DB를 싱가포르에서 서울로 복제했을 때 캐시 적중/미적중 경로의 차이

운영 서비스에는 테스트 코드를 배포하지 않았다. 캐시 적용 이후 측정은
Google IAM 인증이 필요한 별도 비공개 Cloud Run 서비스에서 수행했다.
서울 DB 역시 벤치마크 서비스에만 연결했으며 운영 DB와 운영 Cloud Run
서비스는 변경하지 않았다.

## 환경

| 항목 | 값 |
| --- | --- |
| Cloud Run 리전 | `asia-northeast3` (서울) |
| 컨테이너 사양 | 1 vCPU, 1 GiB |
| 데이터베이스 | Supabase PostgreSQL, `ap-southeast-1` (싱가포르) / `ap-northeast-2` (서울) |
| 데이터베이스 연결 | Supabase transaction pooler |
| 과목 수 | 2,894 |
| 부하 도구 | k6 closed-model VU |
| 요청 간 대기 | 0.2~0.7초 |
| 기능 검증 | 모든 요청의 HTTP 200 검사 |

`portfolio` 프로필은 20초 상승, 60초 상승, 60초 유지, 20초 피크 상승,
40초 피크 유지, 20초 하강으로 구성된다. 200 VU와 1,000 VU 실험은
동일한 요청 비율과 단계 시간을 사용했다.

대상 API는 모두 읽기 전용이다.

- `/api/subjects/count`
- `/api/subjects/departments`
- `/api/subjects/grades`
- `/api/subjects/search`
- `/api/subjects/search/professor`
- `/api/subjects/filter`

## 단계별 해석

### 1. 캐시 단독 효과

동일한 1 vCPU, 1 GiB, 최대 1인스턴스 조건에서 다음과 같이 개선됐다.

- 처리 요청 수: 29,354 -> 49,410, **68.3% 증가**
- 평균 응답 시간: 341.10ms -> 18.67ms, **94.5% 감소**
- p95: 805.79ms -> 29.52ms, **96.3% 감소**
- p99: 1,419.81ms -> 45.81ms, **96.8% 감소**

Prometheus에서 확인한 주요 캐시 적중 값은 다음과 같다.

| 캐시 | hit | miss | 적중률 |
| --- | ---: | ---: | ---: |
| 활성 과목 수 | 9,931 | 1 | 99.99% |
| 학과 목록 | 7,503 | 1 | 99.99% |
| 학년 목록 | 7,433 | 1 | 99.99% |
| 과목명 검색 | 9,953 | 5 | 99.95% |
| 필터 조회 | 7,493 | 7 | 99.91% |

검색/필터 캐시는 입력값을 정규화하고, 과목 데이터 변경 시 커밋 이후
전체 무효화한다. 시간표 담기 수가 바뀌면 인기 순서와 카운트가 낡지
않도록 필터 캐시만 커밋 이후 무효화한다.

### 2. 1,000 VU에서 단일 인스턴스 한계

캐시가 DB 왕복을 대부분 제거해도 1 vCPU 한 대에서는 p95가 1.99초까지
증가했다. 따라서 1,000 VU 구간의 주 병목은 DB 쿼리보다 애플리케이션
CPU, 응답 직렬화, 단일 인스턴스 대기열이다.

### 3. 3대 수평 확장

단일 인스턴스 대비 다음과 같이 개선됐다.

- 처리 요청 수: 94,434 -> 172,792, **83.0% 증가**
- 평균 응답 시간: 783.77ms -> 222.40ms, **71.6% 감소**
- p95: 1,991.06ms -> 793.54ms, **60.1% 감소**

Cloud Run 로그에서 서로 다른 인스턴스 ID 세 개의 캐시 warm-up 완료를
확인했다. 인스턴스당 DB 풀을 10개로 제한해 세 대가 모두 떠도 애플리케이션
연결 상한은 30개다.

다만 자동 확장 중 발생한 소수의 클라이언트 타임아웃 때문에 p99는
2.52초로 증가했다. 최대 인스턴스만 늘리는 것으로 급격한 스파이크의
tail latency가 자동 해결되지는 않는다.

### 4. 5대 확장이 더 낫지 않았던 이유

DB 연결 총량을 40개로 제한하고 최대 5대까지 확장했지만, 3대 대비
처리량은 1.7%만 늘었다. 반면 p95는 5.8%, p99는 11.4% 증가했다.
실제로 다섯 인스턴스 모두 기동됐으며 서버 5xx는 없었다.

이 구간에서는 추가 인스턴스의 콜드 스타트와 각 인스턴스의 로컬 캐시
예열, 큰 검색 응답의 직렬화 비용이 tail latency를 지배한다. 따라서
현재 실험에서는 최대 3대가 처리량과 지연 시간의 더 나은 균형점이다.

### 5. 서울 DB 복제와 데이터 무결성

새 무료 Supabase 프로젝트를 `ap-northeast-2`에 만들고 기존 DB의
`public` 스키마만 복제했다. Supabase의 Auth/Storage 등 시스템 스키마는
덤프에서 제외했고, Data API도 활성화하지 않았다. 애플리케이션은
transaction pooler를 통한 JDBC 연결만 사용한다.

| 테이블 | 싱가포르 | 서울 |
| --- | ---: | ---: |
| `admin_audit_logs` | 22 | 22 |
| `analytics_events` | 0 | 0 |
| `flyway_schema_history` | 10 | 10 |
| `schedules` | 3,682 | 3,682 |
| `subjects` | 2,894 | 2,894 |
| `user_activity_daily` | 9 | 9 |
| `user_majors` | 2,693 | 2,693 |
| `user_timetables` | 14,694 | 14,694 |
| `users` | 2,691 | 2,691 |
| `wishlist_items` | 6,731 | 6,731 |

행 수뿐 아니라 각 테이블 전체 행의 JSON 해시, 9개 시퀀스의 현재 값,
Flyway 실패 이력 0건, 미검증 제약조건 0건까지 양쪽이 일치했다.

캐시 적중 경로에서는 DB 리전 변경의 차이가 거의 없었다.

- 200 VU 처리량: 49,410 -> 49,449, **0.08% 증가**
- 200 VU 평균: 18.67ms -> 19.07ms, **2.1% 증가**
- 1,000 VU 3대 처리량: 172,792 -> 172,904, **0.06% 증가**
- 1,000 VU 3대 평균: 222.40ms -> 221.31ms, **0.5% 감소**

이는 캐시가 DB 왕복을 대부분 제거했기 때문에 정상적인 결과다. 리전
변경만으로 캐시 적중 경로의 성능이 좋아졌다고 주장할 수는 없다.

### 6. DB 민감 경로에서의 서울 리전 효과

DB 왕복 차이를 분리하기 위해 동일한 캐시 적용 이미지에서
`SUBJECT_CACHE_MAXIMUM_SIZE=0`, warm-up 비활성화, 최대 1인스턴스로
설정한 뒤 DB 연결만 바꿔 200 VU 실험을 반복했다.

| DB 리전 | 요청 수 | 실패 | 실패율 | 평균 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 싱가포르 | 15,256 | 29 | 0.1901% | 1,098.56ms | 2,182.09ms | 12,482.86ms |
| 서울 | 27,424 | 0 | 0% | 396.67ms | 980.97ms | 1,478.35ms |

서울 DB는 동일 조건에서 다음과 같이 개선됐다.

- 처리 요청 수: **79.8% 증가**
- 평균 응답 시간: **63.9% 감소**
- p95: **55.0% 감소**
- p99: **88.2% 감소**
- 클라이언트 실패: 29건 -> 0건

두 리비전 모두 Cloud Run 서버 5xx는 0건이었다. 따라서 서울 DB의
가치는 캐시 미스, 캐시 무효화 직후, 쓰기 및 비캐시 API처럼 실제 DB
왕복이 발생하는 경로에서 나타난다.

## 결론

첫 번째 우선순위는 Caffeine 캐시 적용이다. 200 VU 기준 p95를 96.3%
줄였고 오류 없이 처리량을 68.3% 높였다.

운영 수평 확장은 `max-instances=3`, `concurrency=40`,
`DB_POOL_MAXIMUM_SIZE=10`부터 시작하는 것이 합리적이다. 다만 1,000 VU의
급격한 상승에서도 p99를 보장하려면 최소 인스턴스를 미리 확보하거나,
검색 결과 페이지 크기/응답 DTO/직렬화 비용을 별도로 줄여야 한다.

최대 인스턴스를 5대로 늘리는 설정은 이번 부하 형태에서 비용 대비 이점이
확인되지 않았으므로 기본값으로 권장하지 않는다.

서울 DB 이전은 캐시 적중 경로의 처리량을 바꾸지 않았지만, DB 민감
경로에서는 p95를 55.0% 줄이고 실패를 제거했다. 따라서 최종 구성은
`서울 DB + Caffeine 캐시 + 최대 3인스턴스`가 합리적이다. 다만 이번
작업은 검증용 복제이므로 운영 전환 시에는 쓰기 중단 또는 증분 동기화,
최종 건수/해시 재검증, 연결 전환, 롤백 절차가 별도로 필요하다.

## 재현

```bash
BASE_URL="https://<cloud-run-service-url>" \
BENCHMARK_NAME="cache-max3-pool10-1000vus" \
RESULT_FILE="result.json" \
PROFILE="portfolio" \
PEAK_VUS="1000" \
ID_TOKEN="$(gcloud auth print-identity-token)" \
k6 run scripts/k6/subject-read-benchmark.js
```

k6가 `exit 99`로 종료된 실험은 기능 실패를 뜻하지 않는다. 이 스크립트는
`p95 < 500ms`, `p99 < 1000ms`를 성능 합격선으로 두므로, HTTP 오류가
없어도 지연 시간 임계값을 넘으면 99를 반환한다.
